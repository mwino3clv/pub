3  N-Tier-Architektur

NoteLernziele

Nach diesem Kapitel kannst du …

  • erklären, was eine Schicht (Tier) in einem Programm ist und wozu sie dient,
  • die drei Schichten Frontend, Business Logic und Backend benennen und ihre Aufgaben unterscheiden,
  • die Klassen ProductView, ProductService und ProductDao den richtigen Schichten zuordnen,
  • beschreiben, warum eine Schicht nur mit der Schicht direkt darunter kommuniziert,
  • ein einfaches dreischichtiges Programm lesen und verstehen.

3.1 Eine Klasse macht alles — was schiefgehen kann

Stell dir vor, du schreibst eine Klasse ProductManager. Sie soll Produkte anzeigen, berechnen und speichern.

public class ProductManager {
    public void showProducts()     { /* Anzeige */ }
    public void calculateDiscount(){ /* Logik   */ }
    public void saveToFile()       { /* Datei   */ }
}

Das klingt zunächst praktisch. Doch sobald sich etwas ändert, entsteht ein Problem.

Beispiel: Du speicherst Produkte künftig in einer Datenbank statt in einer Datei. Dann musst du ProductManager anfassen — obwohl er eigentlich nur für die Anzeige zuständig sein sollte. Eine Änderung am Datenzugriff kann versehentlich die Anzeige kaputtmachen.

Das ist die Konsequenz, wenn eine Klasse zu viele Verantwortlichkeiten trägt. Die Lösung heißt Trennung der Verantwortlichkeiten — und genau das leistet die N-Tier-Architektur.

3.2 ProductView — konkret betrachtet

Bevor wir das Gesamtmodell einführen, schauen wir uns eine einzelne Klasse an: ProductView.

public class ProductView {
    private ProductService service;

    public ProductView(ProductService service) {
        this.service = service;
    }

    public void showAllProducts() {
        List<Product> products = service.getAll();
        for (Product p : products) {
            System.out.println(p.getName() + " – " + p.getPrice());
        }
    }
}

ProductView hat eine einzige Aufgabe: Produkte auf dem Bildschirm ausgeben. Sie weiß nicht, woher die Produkte stammen. Sie kennt keinen Dateinamen. Sie kennt keine Datenbank. Sie ruft nur service.getAll() auf und gibt die Ergebnisse aus.

Das ist bewusst so. ProductView soll sich nicht darum kümmern müssen, wie Daten gespeichert sind. Ändert sich die Speichermethode, bleibt ProductView unberührt.

TipBeobachtung

ProductView kennt ProductService. ProductService kennt ProductDao. ProductView kennt ProductDao nicht. Jede Klasse kennt nur ihren direkten Nachbarn.

3.3 Das Schichtenmodell im Überblick

N-Tier-Architektur (sprich: „En-Tier”) bedeutet: ein Programm wird in übereinanderliegende Schichten aufgeteilt. „N” steht für eine beliebige Anzahl; in der Praxis sind es meist drei Schichten — deshalb spricht man oft von 3-Tier.

Eine Schicht (englisch: tier oder layer) ist eine Gruppe von Klassen mit einer gemeinsamen Aufgabe. Jede Schicht kommuniziert nur mit der Schicht direkt darunter. Diese Regel hält das Programm übersichtlich.

In unserem Beispiel gibt es drei Schichten:

  • Frontend — ProductView: zeigt Daten an und nimmt Eingaben entgegen
  • Business Logic — ProductService: prüft Eingaben und koordiniert den Ablauf
  • Backend — ProductDao: liest und schreibt Daten

Die Klassen ProductView, ProductService und ProductDao tragen jeweils den Namen ihres Themenbereichs. Das macht den Zweck jeder Klasse sofort erkennbar.

3.4 Frontend — die Präsentationsschicht

Das Frontend ist die Schicht, die mit dem Benutzer kommuniziert. Sie zeigt Daten an und nimmt Eingaben entgegen.

Was das Frontend nicht tut:

  • keine eigene Berechnung, keine Prüfung von Eingaben,
  • kein direkter Datenbankzugriff,
  • keine Entscheidung, wie Daten gespeichert werden.

Das Frontend fragt den Service — und zeigt nur das Ergebnis an.

Erweitertes Beispiel: ProductView mit Eingabe

public class ProductView {
    private ProductService service;

    public ProductView(ProductService service) {
        this.service = service;
    }

    public void showAllProducts() {
        List<Product> products = service.getAll();
        for (Product p : products) {
            System.out.println(p.getId() + " | " + p.getName()
                               + " | " + p.getPrice() + " €");
        }
    }

    public void addProductFromInput(int id, String name, double price) {
        Product p = new Product(id, name, price);
        service.addProduct(p);
        System.out.println("Produkt gespeichert.");
    }
}

ProductView erzeugt ein Product-Objekt aus Eingabewerten und übergibt es an den Service. Sie prüft nicht selbst, ob der Preis gültig ist — das ist die Aufgabe der nächsten Schicht.

3.5 Business Logic — die Logikschicht

Business Logic bedeutet: die Regeln und Abläufe des Programms. Die Logikschicht entscheidet, was mit den Daten passiert.

Die Klasse ProductService prüft Eingaben, koordiniert Abläufe und delegiert den Datenzugriff an das Backend.

public class ProductService {
    private ProductDao dao;

    public ProductService(ProductDao dao) {
        this.dao = dao;
    }

    public List<Product> getAll() {
        return dao.findAll();
    }

    public void addProduct(Product product) {
        if (product.getPrice() < 0) {
            throw new IllegalArgumentException("Preis darf nicht negativ sein.");
        }
        dao.save(product);
    }
}

Zwei Details sind wichtig:

Erstens: ProductService erhält sein dao-Objekt von außen (im Konstruktor). Das heißt, jemand anderes entscheidet, welche konkrete DAO-Variante verwendet wird. ProductService selbst weiß das nicht — und muss es auch nicht wissen.

Zweitens: ProductService hängt vom Interface ProductDao ab, nicht von einer konkreten Klasse wie InMemoryProductDao. Das hat einen entscheidenden Vorteil: Die Speichervariante kann ausgetauscht werden, ohne ProductService zu ändern. Dieses Prinzip wird in Section 3.8 noch einmal aufgegriffen und in Kapitel 3 (SOLID, Abschnitt D) vertieft.

3.6 Backend — die Datenzugriffsschicht

Das Backend ist die Schicht, die mit der Datenquelle kommuniziert. Die Datenquelle kann ein Arbeitsspeicher, eine Datei oder eine Datenbank sein.

Das Backend enthält weder Anzeigelogik noch Geschäftsregeln. Es liefert Daten zurück und speichert sie — mehr nicht.

In unserem Programm ist das Backend als Interface ProductDao definiert. Ein Interface (Schnittstelle) legt fest, welche Methoden es geben muss — aber nicht, wie sie funktionieren. Drei konkrete Klassen setzen dieses Interface um:

Klasse Datenquelle
InMemoryProductDao Arbeitsspeicher (ArrayList)
TextFileProductDao Textdatei (CSV-Format)
MariaDbProductDao Relationale Datenbank (MariaDB)

Das Interface heißt ProductDao. DAO steht für Data Access Object — ein Objekt, das den Datenzugriff kapselt. Das DAO-Pattern wird ausführlich in ?sec-dao-pattern behandelt.

Kurz-Snippet: Das Interface ProductDao

public interface ProductDao {
    List<Product> findAll();
    Product findById(int id);
    void save(Product p);
    void deleteById(int id);
}

Das Interface schreibt vier Methoden vor. Jede Klasse, die ProductDao implementiert, muss alle vier Methoden bereitstellen. ProductService kann sich darauf verlassen — unabhängig davon, welche Implementierung tatsächlich verwendet wird.

3.7 Die Domain-Klasse: Product

Alle drei Schichten arbeiten mit demselben Objekt: Product. Product ist ein einfacher Datenbehälter — er enthält Daten, aber keine Logik.

public class Product {
    private int id;
    private String name;
    private double price;

    public Product(int id, String name, double price) {
        this.id = id;
        this.name = name;
        this.price = price;
    }

    public int getId()       { return id; }
    public String getName()  { return name; }
    public double getPrice() { return price; }
}

Product kennt weder ProductService noch ProductDao. Es ist eine reine Datenklasse — man nennt solche Objekte auch POJO (Plain Old Java Object, zu Deutsch: einfaches Java-Objekt ohne spezielle Abhängigkeiten).

ProductView zeigt es an. ProductService prüft es. ProductDao speichert es. Die Aufgaben sind sauber verteilt.

3.8 Alles zusammen: ein vollständiger Überblick

Hier sieht man das vollständige Bild.

ProductView ruft ProductService auf. ProductService hängt vom Interface ProductDao ab. InMemoryProductDao, TextFileProductDao und MariaDbProductDao implementieren dieses Interface.

Der entscheidende Punkt: ProductService kennt nur ProductDao — das Interface. Welche konkrete Klasse dahintersteckt, entscheidet der Code, der das Programm zusammenbaut (oft main()).

Das macht das Programm flexibel. Möchte man statt einer Textdatei eine Datenbank verwenden, tauscht man die DAO-Implementierung aus. ProductView und ProductService müssen nicht geändert werden.

NoteMerksatz

N-Tier: Jede Schicht hat genau eine Aufgabe. Jede Schicht kennt nur die Schicht direkt darunter. Änderungen bleiben auf eine Schicht beschränkt.

Wie das Programm zusammengebaut wird

// In main() oder einer Startklasse:
ProductDao dao     = new InMemoryProductDao();   // Wahl der Variante
ProductService svc = new ProductService(dao);
ProductView view   = new ProductView(svc);

view.showAllProducts();

Diese drei Zeilen zeigen das Prinzip: Die Abhängigkeiten werden von außen hineingegeben. ProductService bekommt sein dao im Konstruktor. ProductView bekommt seinen service im Konstruktor. Keine der Klassen erzeugt ihre Abhängigkeit selbst. Dieses Muster nennt sich Dependency Injection (Abhängigkeiten von außen einsetzen) — ein Begriff, der in Kapitel 3 bei Prinzip D wieder auftaucht.

3.9 Zusammenfassung

N-Tier-Architektur teilt ein Programm in Schichten auf. Jede Schicht hat genau eine Aufgabe. Jede Schicht kennt nur ihren direkten Nachbarn.

Schicht Klasse Aufgabe
Frontend ProductView Anzeige, Eingabe
Business Logic ProductService Regeln, Ablauf
Backend ProductDao Datenzugriff

Die drei Klassen ProductView, ProductService und ProductDao bilden zusammen das Gerüst des gesamten Begleithefts. Alle weiteren Themen — SOLID-Prinzipien, DAO-Pattern, DAO-Varianten — bauen auf diesem Gerüst auf.

Weiter geht es in Kapitel 3 mit den SOLID-Prinzipien, die erklären, warum diese Aufteilung so sinnvoll ist.
