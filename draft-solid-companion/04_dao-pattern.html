5  Das DAO-Pattern

NoteLernziele

Nach diesem Kapitel kannst du …

  • erklären, was das DAO-Pattern ist und welches Problem es löst,
  • ein ProductDao-Interface mit den vier Standardmethoden schreiben,
  • den Unterschied zwischen Interface und Implementierung beschreiben,
  • erklären, warum ProductService vom Interface abhängt und nicht von einer konkreten Klasse,
  • die drei DAO-Varianten (In-Memory, Textdatei, MariaDB) nach Einsatzzweck unterscheiden.

5.1 Das Problem: direkte Kopplung

Stell dir vor, ProductService enthält direkt den Code für den Datenbankzugriff. Was passiert, wenn du statt einer Datenbank plötzlich eine Textdatei nutzen willst?

Du musst ProductService öffnen und umschreiben. Und wenn danach etwas mit der Anzeige nicht stimmt? Dann ist nicht klar, ob der Fehler in der Logik oder im Datenzugriff steckt.

Das ist das Kernproblem: Business-Logik und Datenzugriff vermischen sich. Eine Änderung an der Datenquelle zieht Änderungen an der Logik nach sich.

// Schlechtes Beispiel: direkter Zugriff ohne Abstraktionsebene
public class ProductService {
    private MariaDbProductDao dao = new MariaDbProductDao();

    public List<Product> getAll() {
        return dao.findAll();
    }
}

ProductService ist jetzt fest mit MariaDbProductDao verbunden. Ein Austausch der Datenquelle ist ohne Codeänderung unmöglich. Das verletzt das Dependency Inversion Principle (→ ?sec-dip).

5.2 Die Lösung: DAO mit Interface

DAO steht für Data Access Object — Datenzugriffsobjekt. Das Muster trennt den Datenzugriff sauber vom Rest des Programms.

Die Grundidee: Ein Interface legt fest, welche Operationen möglich sind. Konkrete Klassen — die Implementierungen — bestimmen, wie diese Operationen ausgeführt werden. ProductService kennt nur das Interface. Welche Implementierung dahintersteckt, ist für den Service irrelevant.

// Das Interface — der "Vertrag"
public interface ProductDao {
    List<Product> findAll();
    Product findById(int id);
    void save(Product product);
    void deleteById(int id);
}

Ein Interface in Java ist eine Schnittstelle: Es definiert Methoden, aber enthält keinen Ausführungscode. Jede Klasse, die das Interface implementiert, muss alle vier Methoden bereitstellen. Das Interface ist der Vertrag — jede Implementierung muss ihn einhalten.

// ProductService hängt vom Interface ab — nicht von einer konkreten Klasse
public class ProductService {
    private ProductDao dao;  // Interface-Typ, kein konkreter Typ

    public ProductService(ProductDao dao) {
        this.dao = dao;
    }

    public List<Product> getAll() {
        return dao.findAll();
    }

    public void addProduct(Product product) {
        dao.save(product);
    }
}

ProductService weiß nicht, ob dao Daten aus dem Arbeitsspeicher, einer Datei oder einer Datenbank liest. Diese Entscheidung trifft der Code, der ProductService erzeugt — und das ist genau so gewollt.

Merksatz: Der Service weiß nicht, wie Daten gespeichert sind. Das ist Absicht.

5.3 Das Interface im Detail

Das ProductDao-Interface enthält genau vier Methoden. Diese vier decken alle grundlegenden Datenzugriffsoperationen ab — bekannt unter dem Kürzel CRUD: Create (Erstellen), Read (Lesen), Update/Save (Speichern), Delete (Löschen).

Methode Aufgabe
findAll() Alle Produkte als Liste zurückgeben
findById(int id) Ein einzelnes Produkt anhand der ID suchen
save(Product p) Ein Produkt speichern (neu anlegen oder aktualisieren)
deleteById(int id) Ein Produkt anhand der ID löschen

Das Interface enthält bewusst nur diese vier Methoden — nicht mehr. Das hält es schlank und klar (→ Interface Segregation Principle, ?sec-isp).

Jede der drei Implementierungsklassen muss alle vier Methoden bereitstellen. Das garantiert, dass sie überall einsetzbar sind, wo ProductDao erwartet wird (→ Liskov Substitution Principle, ?sec-lsp).

// Implementierung für den Arbeitsspeicher
public class InMemoryProductDao implements ProductDao {
    private List<Product> products = new ArrayList<>();

    @Override
    public List<Product> findAll() {
        return products;
    }

    @Override
    public Product findById(int id) {
        for (Product p : products) {
            if (p.getId() == id) return p;
        }
        return null;
    }

    @Override
    public void save(Product product) {
        products.add(product);
    }

    @Override
    public void deleteById(int id) {
        products.removeIf(p -> p.getId() == id);
    }
}

Das Schlüsselwort implements zeigt an, dass eine Klasse ein Interface umsetzt. Die Annotation @Override macht deutlich, dass die Methode aus dem Interface stammt. Fehlt eine der vier Methoden, gibt Java einen Compilerfehler — der Vertrag muss vollständig erfüllt sein.

5.4 Dependency Injection — wer entscheidet?

Wer legt fest, welche Implementierung tatsächlich verwendet wird? Diese Entscheidung trifft der Code, der alles zusammenbaut — typischerweise die main-Methode.

// main-Methode: hier wird die konkrete Implementierung gewählt
public class Main {
    public static void main(String[] args) {
        ProductDao dao = new InMemoryProductDao();   // Entscheidung hier
        ProductService service = new ProductService(dao);
        ProductView view = new ProductView(service);

        view.showAllProducts();
    }
}

Die Implementierung wird als Parameter übergeben — das nennt sich Dependency Injection (Abhängigkeitsinjektion). ProductService erhält sein dao-Objekt von außen, statt es selbst zu erzeugen.

Das hat einen großen Vorteil: Um die Datenquelle zu wechseln, ändert man nur eine einzige Zeile.

// Wechsel zur Datenbankimplementierung — nur diese Zeile ändert sich:
ProductDao dao = new MariaDbProductDao();
// ProductService und ProductView bleiben vollständig unverändert

ProductService und ProductView merken nichts von diesem Wechsel. Sie arbeiten weiterhin mit dem Interface — egal was dahintersteckt.

5.5 Die drei Varianten im Vergleich

Das Interface ProductDao kann auf drei Arten implementiert werden. Alle drei erfüllen denselben Vertrag — die vier Methoden. Sie unterscheiden sich nur darin, wo und wie Daten gespeichert werden.

Kriterium InMemoryProductDao TextFileProductDao MariaDbProductDao
Datenquelle Arbeitsspeicher (ArrayList) Textdatei (CSV-Format) Relationale Datenbank
Persistenz Nein Ja Ja
Einfachheit ★★★ ★★ ★
Praxisnähe Gering Mittel Hoch
Für erste Tests Ideal Gut Eher nicht
Externe Abhängigkeit Keine Keine MariaDB Connector/J

Persistenz bedeutet: Daten bleiben erhalten, wenn das Programm beendet wird. InMemoryProductDao speichert Daten im Arbeitsspeicher — sie verschwinden beim Beenden. TextFileProductDao und MariaDbProductDao schreiben auf dauerhafte Speichermedien.

MariaDB Connector/J ist eine Bibliothek (JAR-Datei), die Java ermöglicht, mit einer MariaDB-Datenbank zu kommunizieren. JDBC (Java Database Connectivity) ist die Standard-Schnittstelle in Java für den Zugriff auf relationale Datenbanken.

Die Details jeder Variante — vollständiger Code, Datenfluss, Fehlerbehandlung — folgen in Chapter 6.

5.6 Variante 1: InMemoryProductDao

Daten werden in einer ArrayList im Arbeitsspeicher gehalten. Es gibt keine Datei, keine Datenbank, keine externe Abhängigkeit.

public class InMemoryProductDao implements ProductDao {
    private List<Product> products = new ArrayList<>();

    @Override
    public List<Product> findAll() {
        return products;
    }

    @Override
    public void save(Product product) {
        products.add(product);
    }

    // findById und deleteById analog aufgebaut
}

Diese Variante eignet sich ideal für den Einstieg und für Tests. Alles läuft im Programm selbst — es braucht nichts weiter. Der Nachteil: Nach dem Programmende sind alle Daten weg.

5.7 Variante 2: TextFileProductDao

Daten werden als einfache Textdatei im CSV-Format gespeichert. CSV steht für Comma-Separated Values — hier wird Semikolon als Trennzeichen verwendet.

1;Laptop;999.99
2;Maus;19.99
3;Tastatur;49.90

Beim Lesen wird jede Zeile am Semikolon aufgeteilt und in ein Product-Objekt umgewandelt. Beim Schreiben wird jedes Product-Objekt in eine Textzeile umgewandelt und gespeichert.

public class TextFileProductDao implements ProductDao {
    private String filename = "products.txt";

    @Override
    public List<Product> findAll() {
        List<Product> result = new ArrayList<>();
        // Datei zeilenweise lesen
        // Jede Zeile mit split(";") aufteilen
        // Für jede Zeile ein Product-Objekt erzeugen
        return result;  // gekürztes Beispiel
    }

    @Override
    public void save(Product product) {
        // Produkt als Zeile an die Datei anhängen
        // Format: id;name;price
    }
}

Die Daten bleiben auch nach dem Programmende erhalten — die Datei liegt auf dem Dateisystem. Die Details dieser Implementierung folgen in Chapter 6.

5.8 Variante 3: MariaDbProductDao

Daten werden in einer relationalen Datenbank gespeichert. MariaDB ist ein freies Datenbanksystem, das SQL versteht. SQL (Structured Query Language) ist die Sprache, mit der Datenbanken abgefragt und verändert werden.

Die Datenbanktabelle für unsere Produkte sieht so aus:

CREATE TABLE product (
    id    INT PRIMARY KEY AUTO_INCREMENT,
    name  VARCHAR(100),
    price DOUBLE
);

Der Java-Code greift über JDBC auf die Datenbank zu:

public class MariaDbProductDao implements ProductDao {
    @Override
    public List<Product> findAll() {
        List<Product> result = new ArrayList<>();
        // JDBC: Verbindung zur Datenbank öffnen
        // SQL-Abfrage ausführen: SELECT id, name, price FROM product
        // Ergebnis (ResultSet) zeilenweise auslesen
        // Für jede Zeile ein Product-Objekt erzeugen
        return result;  // gekürztes Beispiel
    }
}

Diese Variante ist die professionellste — aber auch die komplexeste. Sie benötigt eine laufende Datenbank und die MariaDB Connector/J-Bibliothek im Projekt. Die vollständige Implementierung folgt in Chapter 6.

5.9 Zusammenfassung

Das DAO-Pattern löst ein konkretes Problem: Es trennt den Datenzugriff sauber vom Rest des Programms.

Das Herzstück ist das Interface ProductDao. Es definiert vier Methoden und legt damit fest, was jede Implementierung können muss. ProductService hängt nur von diesem Interface ab — nicht von einer konkreten Klasse.

Die drei Implementierungen InMemoryProductDao, TextFileProductDao und MariaDbProductDao sind austauschbar. Ein Wechsel der Datenquelle erfordert keine Änderung an ProductService oder ProductView.

Das Muster verbindet mehrere SOLID-Prinzipien direkt:

  • SRP (?sec-srp): Datenzugriff ist Aufgabe der DAO-Klasse — nicht des Service.
  • OCP (?sec-ocp): Neue Datenquelle → neue Klasse. Bestehender Code bleibt unberührt.
  • LSP (?sec-lsp): Alle drei Implementierungen sind überall einsetzbar, wo ProductDao erwartet wird.
  • ISP (?sec-isp): Das Interface enthält nur vier notwendige Methoden — nicht mehr.
  • DIP (?sec-dip): ProductService hängt vom Interface ab, nicht von MariaDbProductDao.

Merksatz: Das DAO-Pattern kapselt den gesamten Datenzugriff hinter einem Interface. Der Service weiß nicht, wie Daten gespeichert sind — und das ist genau richtig so.
