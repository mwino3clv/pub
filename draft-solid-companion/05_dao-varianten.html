6  DAO-Varianten im Detail

NoteLernziele

Nach diesem Kapitel kannst du …

  • erklären, was die drei DAO-Varianten unterscheidet,
  • InMemoryProductDao vollständig lesen und schreiben,
  • das Dateiformat von TextFileProductDao beschreiben und den Lese- und Schreibvorgang erklären,
  • die wesentlichen JDBC-Schritte für MariaDbProductDao benennen,
  • entscheiden, welche Variante für eine konkrete Aufgabe geeignet ist,
  • den Zusammenhang mit den SOLID-Prinzipien DIP, OCP und SRP erklären.

Das Interface ProductDao legt einen Vertrag fest: vier Methoden, die jede Implementierung bereitstellen muss. Was hinter diesem Vertrag steckt, kann völlig verschieden sein — eine Liste im Arbeitsspeicher, eine Textdatei auf der Festplatte oder eine relationale Datenbank.

Dieses Kapitel zeigt alle drei Varianten im Detail. Es setzt voraus, dass du Section 5.3 (das Interface und seinen Aufbau) bereits kennst.

6.1 Wiederholung: Interface und Implementierungen

Alle drei Klassen implementieren dasselbe Interface. Das bedeutet: Jede Klasse stellt dieselben vier Methoden bereit. ProductService kennt nur das Interface — er weiß nicht, welche Klasse dahintersteckt.

// ProductService hängt vom Interface ab — nicht von einer konkreten Klasse
public class ProductService {
    private ProductDao dao;

    public ProductService(ProductDao dao) {
        this.dao = dao;
    }

    public List<Product> getAll() {
        return dao.findAll();
    }
}

Die konkrete Implementierung wird von außen übergeben. Das erlaubt einen Wechsel der Datenquelle ohne Änderung an ProductService.

6.2 Die Domänenklasse Product

Alle drei Varianten arbeiten mit demselben Objekt: Product.

public class Product {
    private int id;
    private String name;
    private double price;

    public Product(int id, String name, double price) {
        this.id    = id;
        this.name  = name;
        this.price = price;
    }

    public int    getId()    { return id; }
    public String getName()  { return name; }
    public double getPrice() { return price; }
}

Product ist ein reines Datenobjekt — es enthält nur Daten und Getter. Keine Datenbankverbindung, keine Dateioperationen. Diese Trennung ist beabsichtigt: Das Objekt weiß nicht, wie es gespeichert wird.

6.3 Variante 1: InMemoryProductDao

Daten werden in einer ArrayList im Arbeitsspeicher gehalten. Es gibt keine Datei und keine Datenbank. Alles läuft innerhalb des laufenden Programms.

In-Memory bedeutet wörtlich „im Speicher” — die Daten liegen im RAM des Computers. Sie verschwinden, sobald das Programm beendet wird. Das ist kein Fehler, sondern die bewusste Eigenschaft dieser Variante.

6.3.1 Vollständige Implementierung

public class InMemoryProductDao implements ProductDao {

    private List<Product> products = new ArrayList<>();

    @Override
    public List<Product> findAll() {
        return products;
    }

    @Override
    public Product findById(int id) {
        for (Product p : products) {
            if (p.getId() == id) return p;
        }
        return null;
    }

    @Override
    public void save(Product product) {
        products.add(product);
    }

    @Override
    public void deleteById(int id) {
        products.removeIf(p -> p.getId() == id);
    }
}

findById gibt null zurück, wenn kein Produkt mit der gesuchten ID existiert. Das ist eine vereinfachte Konvention — im echten Produktionscode würde man hier Optional<Product> verwenden.

deleteById nutzt removeIf mit einem Lambda-Ausdruck: p -> p.getId() == id. Ein Lambda ist eine kurze Schreibweise für eine anonyme Funktion. removeIf entfernt alle Elemente aus der Liste, für die diese Bedingung zutrifft.

6.3.2 Vorteile und Grenzen

InMemoryProductDao
✓ Vorteile Sehr einfach, keine externe Abhängigkeit, ideal für Tests
✗ Grenzen Keine Persistenz — Daten verschwinden beim Programmende
✓ Wann einsetzen Entwicklung, Tests, erste Implementierung

Persistenz bezeichnet die Eigenschaft, dass Daten auch nach dem Programmende erhalten bleiben. InMemoryProductDao hat diese Eigenschaft nicht — das macht sie für den Einstieg ideal, für produktive Anwendungen aber ungeeignet.

Merksatz: InMemoryProductDao — kein Setup, kein Aufwand, kein Datenverlust-Risiko. Perfekt zum Starten und Testen.

6.4 Variante 2: TextFileProductDao

Daten werden als einfache Textdatei auf dem Dateisystem gespeichert. Die Datei bleibt auch nach dem Programmende erhalten — das ist der entscheidende Unterschied zu InMemoryProductDao.

6.4.1 Das Dateiformat

Das Format ist CSV (Comma-Separated Values — tatsächlich hier mit Semikolon als Trennzeichen, weil Kommas in deutschen Dezimalzahlen problematisch sind):

id;name;price
1;Laptop;999.99
2;Maus;19.99
3;Tastatur;49.99

Jede Zeile entspricht einem Produkt. Die erste Zeile ist der Header — sie enthält die Spaltennamen und wird beim Lesen übersprungen. Die drei Felder id, name und price sind durch Semikolon getrennt.

6.4.2 Lesen: findAll()

public class TextFileProductDao implements ProductDao {

    private String filename = "products.txt";

    @Override
    public List<Product> findAll() {
        List<Product> result = new ArrayList<>();
        // Datei zeilenweise lesen (BufferedReader)
        // Erste Zeile (Header) überspringen
        // Jede Datenzeile aufteilen: String[] parts = line.split(";")
        // Product erzeugen:
        //   int    id    = Integer.parseInt(parts[0]);
        //   String name  = parts[1];
        //   double price = Double.parseDouble(parts[2]);
        //   result.add(new Product(id, name, price));
        return result; // gekürztes Beispiel
    }
}

split(";") teilt eine Textzeile an jedem Semikolon auf und liefert ein String-Array. Integer.parseInt wandelt einen Text wie "1" in die Zahl 1 um. Double.parseDouble macht dasselbe für Dezimalzahlen.

Der vollständige Code würde einen BufferedReader verwenden und eine IOException behandeln — das ist hier vereinfacht dargestellt.

6.4.3 Schreiben: save()

@Override
public void save(Product product) {
    // Alle bestehenden Produkte laden
    List<Product> all = findAll();
    // Neues Produkt hinzufügen
    all.add(product);
    // Gesamte Liste neu in die Datei schreiben
    // BufferedWriter: jede Zeile im Format id;name;price
    // gekürztes Beispiel
}

save() schreibt bei jedem Aufruf die gesamte Datei neu. Das ist einfach zu verstehen, aber langsam bei großen Datenmengen. Für kleinere Anwendungen ist dieser Ansatz ausreichend.

deleteById funktioniert nach demselben Prinzip: alle Produkte lesen, das zu löschende weglassen, den Rest neu schreiben.

6.4.4 Vorteile und Grenzen

TextFileProductDao
✓ Vorteile Persistenz, keine Datenbank nötig, Datei ist lesbar
✗ Grenzen Langsam bei vielen Daten, keine Transaktionen, fehleranfällig bei Sonderzeichen
✓ Wann einsetzen Einfache Anwendungen, wenn keine Datenbank verfügbar ist

Keine Transaktionen bedeutet: Wenn das Programm beim Schreiben abstürzt, kann die Datei halb beschrieben und damit defekt sein. Datenbanken lösen dieses Problem durch Transaktionssicherheit.

Sonderzeichen im Produktnamen können das Format beschädigen: Ein Semikolon im Namen würde beim Lesen fälschlicherweise als Feldtrenner erkannt.

Merksatz: TextFileProductDao — Persistenz ohne Datenbank. Gut für einfache Fälle, aber nicht für professionelle Anwendungen.

6.5 Variante 3: MariaDbProductDao

Daten werden in einer relationalen Datenbank gespeichert. Eine relationale Datenbank speichert Daten in Tabellen — ähnlich wie eine Tabellenkalkulation, aber mit leistungsfähigen Abfragemöglichkeiten.

MariaDB ist ein relationales Datenbanksystem. Es ist Open Source und kompatibel mit MySQL.

JDBC (Java Database Connectivity) ist die Standard-Schnittstelle in Java für den Zugriff auf relationale Datenbanken. JDBC ist Teil von Java — es muss nicht extra installiert werden.

MariaDB Connector/J ist die konkrete Bibliothek, die JDBC für MariaDB umsetzt. Sie liegt als JAR-Datei vor und muss im Projekt eingebunden sein. Ohne diese Datei kann Java nicht mit MariaDB kommunizieren.

6.5.1 Die Tabelle product in MariaDB

Bevor der DAO Daten speichern kann, muss die Tabelle in der Datenbank angelegt werden:

CREATE TABLE product (
    id    INT PRIMARY KEY AUTO_INCREMENT,
    name  VARCHAR(100),
    price DOUBLE
);

AUTO_INCREMENT bedeutet: MariaDB vergibt die id automatisch. PRIMARY KEY bedeutet: Jede Zeile hat eine eindeutige id. VARCHAR(100) ist eine Zeichenkette mit maximal 100 Zeichen.

Die vier SQL-Grundbefehle, die der DAO verwendet:

-- Alle Produkte lesen
SELECT id, name, price FROM product;

-- Produkt einfügen
INSERT INTO product (name, price) VALUES ('Laptop', 999.99);

-- Produkt löschen
DELETE FROM product WHERE id = 1;

-- Produkt aktualisieren (nicht im Interface, hier zur Vollständigkeit)
UPDATE product SET price = 899.99 WHERE id = 1;

6.5.2 Lesen: findAll()

public class MariaDbProductDao implements ProductDao {

    @Override
    public List<Product> findAll() {
        List<Product> result = new ArrayList<>();
        // 1. Connection öffnen (DriverManager.getConnection)
        // 2. PreparedStatement erstellen:
        //    "SELECT id, name, price FROM product"
        // 3. Abfrage ausführen: stmt.executeQuery()
        // 4. ResultSet zeilenweise auslesen:
        //    result.add(new Product(rs.getInt("id"),
        //                          rs.getString("name"),
        //                          rs.getDouble("price")));
        // 5. Connection schließen
        return result; // gekürztes Beispiel
    }
}

Der vollständige Code öffnet eine Connection über DriverManager.getConnection() mit URL, Benutzername und Passwort. Dann wird ein PreparedStatement mit der SQL-Abfrage erstellt. Das ResultSet enthält die Ergebniszeilen — es wird zeilenweise mit rs.next() durchlaufen.

6.5.3 Schreiben: save()

@Override
public void save(Product product) {
    // 1. Connection öffnen
    // 2. PreparedStatement mit Platzhaltern:
    //    "INSERT INTO product (name, price) VALUES (?, ?)"
    // 3. Parameter setzen:
    //    stmt.setString(1, product.getName());
    //    stmt.setDouble(2, product.getPrice());
    // 4. Ausführen: stmt.executeUpdate()
    // 5. Connection schließen
    // gekürztes Beispiel
}

Die ?-Zeichen sind Platzhalter im PreparedStatement. Sie werden mit setString, setInt oder setDouble befüllt. Dieser Ansatz ist sicherer als das direkte Einbauen von Werten in den SQL-Text, weil er SQL-Injection verhindert. SQL-Injection ist ein Angriff, bei dem schädliche SQL-Befehle in Eingabefelder eingeschleust werden.

executeUpdate() wird für INSERT, UPDATE und DELETE verwendet. executeQuery() wird für SELECT verwendet.

6.5.4 Vorteile und Grenzen

MariaDbProductDao
✓ Vorteile Persistenz, skalierbar, transaktionssicher, professionell
✗ Grenzen Höhere Komplexität, externe Abhängigkeit (Connector/J), Datenbank muss laufen
✓ Wann einsetzen Produktive Anwendungen, größere Datenmengen

Transaktionssicher bedeutet: Wenn beim Schreiben etwas schiefgeht, rollt die Datenbank automatisch zurück — die Daten bleiben konsistent. Diese Eigenschaft nennt man Transaktionsintegrität.

Merksatz: MariaDbProductDao — professionell und skalierbar. Erfordert Vorbereitung, bietet aber die höchste Zuverlässigkeit.

6.6 Der Datenfluss im Überblick

ProductView ruft getAll() auf ProductService auf. ProductService ruft dao.findAll() auf — er kennt nur das Interface ProductDao. Welche Implementierung dahintersteckt, ist für ProductService unsichtbar.

Die „Datenquelle” im Diagramm steht für alle drei Varianten: eine ArrayList, eine Textdatei oder eine MariaDB-Datenbank. Der Aufruffluss ist in allen drei Fällen gleich.

6.8 Verbindung zu SOLID

Das DAO-Pattern ist ein konkretes Beispiel dafür, wie SOLID-Prinzipien zusammenspielen.

6.8.1 DIP — Dependency Inversion Principle

Abhängig sein vom Interface — nicht von der konkreten Klasse.

// Unerwünscht: fest verdrahtet
ProductService service = new ProductService(new MariaDbProductDao());

// Empfohlen: Implementierung von außen übergeben
ProductDao dao = new InMemoryProductDao();
ProductService service = new ProductService(dao);

ProductService bleibt unverändert — egal welche Variante verwendet wird. Die Entscheidung, welche Implementierung eingesetzt wird, trifft der Code, der ProductService und ProductDao zusammenbaut. Dieses Muster nennt sich Dependency Injection — Abhängigkeiten werden von außen hineingegeben, nicht intern erzeugt.

6.8.2 OCP — Open/Closed Principle

Offen für Erweiterung, geschlossen für Änderung.

Eine neue Datenquelle hinzufügen heißt: eine neue Klasse schreiben.

public class XmlFileProductDao implements ProductDao {
    // Neue Implementierung — bestehender Code bleibt unverändert
}

ProductService, ProductView und das Interface ProductDao müssen nicht angefasst werden.

6.8.3 SRP — Single Responsibility Principle

Eine Klasse hat genau eine Aufgabe.

Klasse Aufgabe
ProductView Anzeige
ProductService Geschäftslogik
InMemoryProductDao Datenzugriff — Arbeitsspeicher
TextFileProductDao Datenzugriff — Datei
MariaDbProductDao Datenzugriff — Datenbank

Jede DAO-Implementierung kennt genau eine Art des Datenzugriffs. SRP, OCP und DIP greifen hier direkt ineinander — das zeigt, dass SOLID-Prinzipien keine isolierten Regeln sind, sondern sich gegenseitig verstärken.

6.9 Zusammenfassung

Dieses Kapitel hat die drei DAO-Varianten im Detail gezeigt.

Alle drei implementieren dasselbe Interface ProductDao. Sie unterscheiden sich nur darin, wo und wie Daten gespeichert werden.

InMemoryProductDao ist die einfachste Variante. Sie speichert Daten in einer ArrayList im Arbeitsspeicher. Sie eignet sich für Tests und erste Implementierungen.

TextFileProductDao speichert Daten in einer CSV-Datei. Die Daten bleiben nach dem Programmende erhalten. Sie ist verständlicher als die Datenbankversion, aber langsamer und fehleranfälliger.

MariaDbProductDao kommuniziert über JDBC mit einer relationalen Datenbank. Sie ist die professionellste Variante: persistent, skalierbar und transaktionssicher. Sie erfordert den MariaDB Connector/J und eine laufende Datenbank.

Das Interface macht alle drei Varianten austauschbar. ProductService und ProductView bleiben in allen Fällen unverändert. Genau das ist der Kern des DAO-Patterns — und das direkte Ergebnis von DIP.

Merksätze:

Der DAO kapselt den Datenzugriff. Service und View wissen nicht, wie Daten gespeichert sind.

Alle drei Varianten erfüllen denselben Vertrag — sie sind jederzeit austauschbar.

In-Memory: einfach, kein Setup, keine Persistenz — ideal zum Starten.

Textdatei: Persistenz ohne Datenbank — gut für einfache Fälle.

MariaDB: professionell und skalierbar — erfordert Connector/J und Datenbank.
