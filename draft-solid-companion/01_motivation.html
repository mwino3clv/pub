2  Warum Programme Struktur brauchen

NoteLernziele

Nach diesem Kapitel kannst du …

  • erklären, warum Programme ohne Struktur schwer wartbar werden.
  • typische Probleme in unstrukturiertem Code benennen.
  • das Prinzip der Trennung von Verantwortlichkeiten in eigenen Worten beschreiben.
  • einschätzen, welchen Nutzen eine klare Aufteilung in Schichten bietet.

2.1 Wachsender Code — ein realistisches Szenario

Jedes Programm beginnt klein. Drei Klassen, ein paar Methoden — alles überschaubar.

Doch Programme wachsen. Neue Funktionen kommen dazu. Fehler werden behoben. Anforderungen ändern sich. Nach einigen Wochen hat dasselbe Projekt zwanzig Klassen und tausende Zeilen Code.

Das ist normal. Das Problem entsteht nicht durch die Größe, sondern durch fehlende Struktur.

2.2 Typische Probleme ohne Struktur

Ohne klare Struktur treten immer wieder dieselben Probleme auf.

Problem 1: Fehler breiten sich aus. Eine Korrektur an einer Stelle erzeugt einen neuen Fehler an einer ganz anderen Stelle. Die Klassen kennen sich gegenseitig zu gut — eine Änderung zieht immer eine Kette nach sich.

Problem 2: Unklare Zuständigkeit. Mit der Zeit weiß niemand mehr genau, welche Klasse wofür zuständig ist. Speichert ProductView die Daten? Oder ProductService? Oder vielleicht beide? Solche Unklarheiten führen zu doppeltem Code und widersprüchlichem Verhalten.

Problem 3: Änderungen werden riskant. Wer eine Funktion erweitern will, muss erst verstehen, wie alles zusammenhängt. Das kostet Zeit — und jede Änderung kann etwas Unerwartetes kaputt machen.

Diese drei Probleme haben eine gemeinsame Ursache: Der Code vermischt Aufgaben, die eigentlich getrennt gehören.

2.3 Die Idee: Verantwortlichkeiten trennen

Die Lösung ist einfach zu verstehen, aber konsequent umzusetzen: Jede Klasse übernimmt genau eine klar abgegrenzte Aufgabe.

In einem gut strukturierten Programm gibt es drei grundlegende Arten von Aufgaben:

  • Anzeigen — Daten auf dem Bildschirm ausgeben, Eingaben entgegennehmen.
  • Verarbeiten — Regeln prüfen, Berechnungen durchführen, Abläufe steuern.
  • Speichern — Daten lesen und schreiben, egal ob in einer Liste, Datei oder Datenbank.

Jede dieser Aufgaben bekommt ihre eigene Klasse. Die Klassen kommunizieren miteinander, aber jede bleibt in ihrem Bereich.

Dieses Prinzip hat einen Namen: Separation of Concerns — auf Deutsch: Trennung der Zuständigkeiten. Es ist einer der wichtigsten Grundsätze in der Softwareentwicklung.

Merksatz: Eine Klasse, eine Aufgabe. Wer alles macht, macht nichts richtig.

2.4 Konkret: Die Produktverwaltung

Durch das gesamte Heft hindurch wird ein konkretes Beispiel verwendet: eine einfache Produktverwaltung.

Ein Product hat drei Eigenschaften: eine eindeutige Nummer (id), einen Namen (name) und einen Preis (price).

Drei Klassen teilen sich die Arbeit auf:

  • ProductView — zuständig für die Ausgabe und Eingabe.
  • ProductService — zuständig für die Geschäftslogik, also die Regeln des Programms.
  • ProductDao — zuständig für das Lesen und Speichern der Daten.

DAO steht für Data Access Object — ein Objekt, das den Zugriff auf Daten kapselt. Was das genau bedeutet und warum es ein eigenes Muster verdient, zeigt ?sec-dao-pattern.

Hier das Grundgerüst der Datenklasse:

// Kurz-Snippet: die Datenklasse Product
class Product {
    int id;
    String name;
    double price;
}

Und eine vollständigere Version mit Konstruktor und toString-Methode:

// Erweitertes Beispiel: Product mit Konstruktor und Ausgabe
class Product {
    private int id;
    private String name;
    private double price;

    public Product(int id, String name, double price) {
        this.id = id;
        this.name = name;
        this.price = price;
    }

    public int getId()       { return id; }
    public String getName()  { return name; }
    public double getPrice() { return price; }

    @Override
    public String toString() {
        return id + " | " + name + " | " + price + " €";
    }
}

Diese Klasse ist reine Daten. Sie enthält keine Logik und keine Datenbankzugriffe. Genau das ist der Punkt: Jede Klasse bleibt bei ihrer Aufgabe.

2.5 Zusammenfassung

Programme wachsen. Wer früh auf Struktur setzt, vermeidet späteres Chaos.

Das zentrale Prinzip heißt Separation of Concerns: Jede Klasse trägt genau eine Verantwortung. In der Produktverwaltung sind das ProductView, ProductService und ProductDao.

Die nächsten Kapitel zeigen, wie dieses Prinzip konkret umgesetzt wird — zunächst als N-Tier-Architektur (?sec-n-tier), dann verfeinert durch die SOLID-Prinzipien (?sec-solid) und schließlich beim DAO-Pattern (?sec-dao-pattern) angewendet.
