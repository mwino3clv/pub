4  SOLID-Prinzipien

NoteLernziele

Nach diesem Kapitel kannst du …

  • die fünf SOLID-Prinzipien benennen und in einem Satz erklären,
  • das Single Responsibility Principle an einem Beispiel erkennen und begründen,
  • das Open/Closed Principle auf das DAO-Pattern anwenden,
  • das Liskov Substitution Principle im Kontext von ProductDao einordnen,
  • das Interface Segregation Principle als Gestaltungsregel für Interfaces verstehen,
  • das Dependency Inversion Principle erklären und zeigen, warum ProductService vom Interface ProductDao — nicht von einer konkreten Klasse — abhängen soll,
  • die Verbindung zwischen DIP und dem DAO-Pattern (Kapitel 4) beschreiben.

4.1 Fünf Prinzipien — eine gemeinsame Idee

SOLID ist eine Sammlung von fünf Prinzipien für den Entwurf objektorientierter Software. Der Name ist ein Akronym — jeder Buchstabe steht für ein Prinzip. Robert C. Martin (bekannt als „Uncle Bob”) hat diese Prinzipien Anfang der 2000er-Jahre formuliert und popularisiert.

Die Prinzipien sind keine starren Regeln. Sie sind Leitlinien. Wer sie kennt, erkennt Schwachstellen im eigenen Code früher — und vermeidet sie beim Schreiben gleich.

In diesem Kapitel werden S, O und D ausführlicher behandelt, denn sie treten im Zusammenhang mit dem DAO-Pattern besonders deutlich auf. L und I werden kürzer gehalten — sie spielen im weiteren Verlauf eine ergänzende Rolle.

4.2 S — Single Responsibility Principle

Single Responsibility Principle (SRP): Eine Klasse hat genau eine Aufgabe — und damit genau einen Grund, sich zu ändern.

4.2.1 Das Problem: zu viele Aufgaben in einer Klasse

Schau dir folgenden Code an:

public class ProductManager {
    public void showProducts()      { /* Anzeige    */ }
    public void calculateDiscount() { /* Logik      */ }
    public void saveToFile()        { /* Datenzugriff */ }
}

Diese Klasse macht drei Dinge gleichzeitig. Das klingt praktisch, ist aber ein Problem.

Angenommen, du willst die Speicherung von einer Textdatei auf eine Datenbank umstellen. Dann musst du ProductManager ändern — obwohl er eigentlich nur für die Anzeige zuständig sein sollte. Eine Änderung am Datenzugriff kann versehentlich die Anzeigefunktion kaputtmachen. Das nennt man eine unbeabsichtigte Kopplung — zwei Dinge hängen zusammen, obwohl sie es nicht sollten.

Kopplung (englisch: coupling) bezeichnet, wie stark Klassen voneinander abhängen. Starke Kopplung macht Änderungen riskant. Schwache Kopplung macht Code wartbar.

4.2.2 Die Lösung: eine Aufgabe pro Klasse

public class ProductView {
    // Einzige Aufgabe: Produkte anzeigen
    public void showAllProducts(List<Product> products) {
        for (Product p : products) {
            System.out.println(p.getName() + " – " + p.getPrice());
        }
    }
}
Klasse Einzige Aufgabe Grund zur Änderung
ProductView Anzeige Ausgabeformat ändert sich
ProductService Geschäftslogik Prüfregeln ändern sich
ProductDao Datenzugriff Speicherort ändert sich

Jetzt ist klar, was geändert werden muss — und was nicht. Wenn das Ausgabeformat wechselt, ändert sich nur ProductView. Der Rest bleibt unberührt.

4.2.3 Erweitertes Beispiel: SRP in Aktion

// Verletzung: Service speichert selbst
public class ProductService {
    public void addProduct(Product p) {
        // Geschäftslogik
        if (p.getPrice() < 0) throw new IllegalArgumentException("Preis ungültig");
        // Datenzugriff — gehört hier NICHT hin
        writeToFile(p);
    }

    private void writeToFile(Product p) { /* ... */ }
}

// Korrekt: Service delegiert an DAO
public class ProductService {
    private ProductDao dao;

    public ProductService(ProductDao dao) {
        this.dao = dao;
    }

    public void addProduct(Product p) {
        if (p.getPrice() < 0) throw new IllegalArgumentException("Preis ungültig");
        dao.save(p); // Speichern ist Aufgabe des DAO
    }
}

Der ProductService prüft die Eingabe — das ist seine Aufgabe. Das Speichern delegiert er an ProductDao — das ist dessen Aufgabe.

TipMerksatz

Eine Klasse ändert sich nur aus einem Grund. Wenn du mehrere Gründe für eine Änderung aufzählen kannst, trägt die Klasse zu viel Verantwortung.

4.3 O — Open/Closed Principle

Open/Closed Principle (OCP): Eine Klasse soll offen für Erweiterung sein — aber geschlossen für Änderung.

4.3.1 Was das bedeutet

„Offen für Erweiterung” heißt: Neue Funktionalität ist möglich. „Geschlossen für Änderung” heißt: Bestehender, funktionierender Code wird dafür nicht angetastet.

Das klingt widersprüchlich. Es ist es nicht — wenn man mit Interfaces arbeitet.

4.3.2 Das Problem ohne OCP

public class ProductService {
    public List<Product> getAll(String type) {
        if (type.equals("memory")) {
            // Daten aus dem Speicher lesen
        } else if (type.equals("file")) {
            // Daten aus einer Datei lesen
        } else if (type.equals("db")) {
            // Daten aus der Datenbank lesen
        }
        return null;
    }
}

Hier steckt das Problem: Wenn eine neue Datenquelle hinzukommt — zum Beispiel eine XML-Datei — muss diese Methode geändert werden. Jede Änderung ist ein Risiko. Man könnte aus Versehen etwas kaputt machen, das vorher funktioniert hat.

4.3.3 Die Lösung: Interface + neue Klasse

// ProductService bleibt für immer unverändert
public class ProductService {
    private ProductDao dao;

    public ProductService(ProductDao dao) {
        this.dao = dao;
    }

    public List<Product> getAll() {
        return dao.findAll(); // Unverändert — egal welche Variante
    }
}

Neue Datenquelle? Neue Klasse schreiben, ProductDao implementieren — fertig. ProductService wird nicht angefasst.

4.3.4 Erweitertes Beispiel: neue Variante ohne Codeänderung

// Neue Datenquelle als neue Klasse — bestehender Code bleibt unberührt
public class XmlFileProductDao implements ProductDao {
    @Override
    public List<Product> findAll() {
        // XML-Datei lesen und Produkte zurückgeben
        return new ArrayList<>();
    }
    @Override
    public Product findById(int id)      { return null; }
    @Override
    public void save(Product p)          { /* in XML schreiben */ }
    @Override
    public void deleteById(int id)       { /* aus XML löschen */ }
}

// Verwendung — ProductService merkt keinen Unterschied
ProductDao dao = new XmlFileProductDao();
ProductService service = new ProductService(dao);

ProductService, ProductView und das Interface ProductDao werden nicht angefasst. Die Erweiterung findet vollständig in der neuen Klasse statt.

Das ist OCP in der Praxis.

TipMerksatz

Neue Anforderungen → neue Klassen. Nicht: bestehende Klassen aufschneiden und umschreiben.

4.4 L — Liskov Substitution Principle

Liskov Substitution Principle (LSP): Überall, wo ein Objekt eines Typs erwartet wird, muss ein Objekt eines Untertyps korrekt funktionieren.

Das Prinzip geht auf Barbara Liskov zurück, die es 1987 formulierte. Untertyp bedeutet hier: eine Klasse, die ein Interface implementiert (oder eine Klasse erweitert).

4.4.1 Im Kontext von ProductDao

ProductService erwartet ein Objekt vom Typ ProductDao — also vom Interface. Alle drei Implementierungen erfüllen diesen Typ:

ProductDao dao = new InMemoryProductDao();  // Variante 1
// ProductDao dao = new TextFileProductDao(); // Variante 2
// ProductDao dao = new MariaDbProductDao();  // Variante 3

ProductService service = new ProductService(dao);
service.getAll(); // Funktioniert mit jeder Variante

ProductService kann mit jeder dieser Varianten arbeiten — ohne Anpassung. Das ist LSP.

4.4.2 Was LSP in der Praxis bedeutet

LSP verletzt man, wenn eine Implementierung das Interface zwar syntaktisch erfüllt, sich aber nicht so verhält, wie das Interface es verspricht.

Ein Beispiel für eine LSP-Verletzung im Geist:

public class BrokenProductDao implements ProductDao {
    @Override
    public List<Product> findAll() {
        return null; // Verspricht eine Liste — liefert null
    }
    // ... weitere Methoden
}

Das Interface verspricht eine Liste. null zurückzugeben verletzt dieses Versprechen. Code, der auf die Liste verlässt, würde abstürzen.

TipMerksatz

Wer ein Interface implementiert, muss sich auch wirklich so verhalten, wie das Interface es verspricht — nicht nur syntaktisch, sondern inhaltlich.

4.5 I — Interface Segregation Principle

Interface Segregation Principle (ISP): Viele kleine, spezifische Interfaces sind besser als ein großes, allgemeines.

4.5.1 Das Problem mit zu großen Interfaces

Stell dir ein Interface mit zwanzig Methoden vor. Eine Klasse, die dieses Interface implementiert, braucht aber nur drei davon. Trotzdem muss sie alle zwanzig ausprogrammieren — auch die sinnlosen.

Das ist Ballast. Und jede ungenutzte Methode ist eine Fehlerquelle.

4.5.2 ISP bei ProductDao

ProductDao enthält genau die vier Methoden, die für den Datenzugriff auf Produkte nötig sind:

public interface ProductDao {
    List<Product> findAll();
    Product findById(int id);
    void save(Product p);
    void deleteById(int id);
}

Nicht mehr, nicht weniger. Jede Implementierungsklasse braucht alle vier — keine Methode ist überflüssig.

Würde das Interface auch Methoden für Berichte, Statistiken oder Protokollierung enthalten, wäre es zu groß. Dann sollten diese Methoden in eigene Interfaces ausgelagert werden.

TipMerksatz

Ein Interface soll nur das enthalten, was jede implementierende Klasse auch tatsächlich braucht.

4.6 D — Dependency Inversion Principle

Dependency Inversion Principle (DIP): Klassen sollen von Abstraktionen (Interfaces) abhängen — nicht von konkreten Implementierungen.

DIP ist das konzeptionelle Scharnier zwischen den SOLID-Prinzipien und dem DAO-Pattern. Es erklärt, warum das ProductDao-Interface überhaupt existiert.

4.6.1 Das Problem: direkte Abhängigkeit

public class ProductService {
    private MariaDbProductDao dao; // konkreter Typ!

    public ProductService() {
        this.dao = new MariaDbProductDao();
    }

    public List<Product> getAll() {
        return dao.findAll();
    }
}

ProductService kennt jetzt MariaDbProductDao — eine ganz konkrete Klasse. Was passiert, wenn du auf eine Textdatei wechseln willst? Du musst ProductService ändern. Eine Klasse, die eigentlich nur Geschäftslogik enthält, muss wegen einer technischen Entscheidung (Datenspeicherung) angepasst werden. Das ist die direkte Konsequenz einer starken Kopplung.

Abhängigkeit (englisch: dependency) bezeichnet, welche anderen Klassen oder Interfaces eine Klasse kennt und benutzt. Je mehr konkrete Klassen eine Klasse kennt, desto schwerer ist sie zu ändern.

4.6.2 Die Lösung: Abhängigkeit vom Interface

public class ProductService {
    private ProductDao dao; // Interface-Typ!

    public ProductService(ProductDao dao) {
        this.dao = dao; // konkrete Klasse kommt von außen
    }

    public List<Product> getAll() {
        return dao.findAll();
    }

    public void addProduct(Product p) {
        if (p.getPrice() < 0) throw new IllegalArgumentException("Preis ungültig");
        dao.save(p);
    }
}

ProductService kennt nur ProductDao — das Interface. Er weiß nicht, ob dahinter InMemoryProductDao, TextFileProductDao oder MariaDbProductDao steckt. Das interessiert ihn auch nicht.

4.6.3 Erweitertes Beispiel: Zusammenbau außerhalb des Service

// Der "Aufbau-Code" — entscheidet, welche Variante verwendet wird
// Variante für erste Tests:
ProductDao dao = new InMemoryProductDao();

// Variante für produktiven Betrieb — nur diese Zeile tauschen:
// ProductDao dao = new MariaDbProductDao();

ProductService service = new ProductService(dao);
ProductView view = new ProductView(service);

view.showAllProducts();

Nur eine einzige Zeile muss geändert werden, um die gesamte Datenzugriffsschicht auszutauschen. ProductService und ProductView bleiben unverändert.

Dieses Muster — die konkrete Klasse von außen übergeben — nennt sich Dependency Injection (englisch für „Abhängigkeit einspritzen”). ProductService fordert nicht selbst eine Implementierung an. Er bekommt sie übergeben.

4.6.4 DIP und das ProductDao-Interface

Das ProductDao-Interface ist direkte Folge des DIP. Ohne dieses Interface könnte ProductService nicht abstrakt bleiben. Er müsste sich für eine konkrete Implementierung entscheiden — und wäre damit eng an sie gekoppelt.

Das Interface definiert einen Vertrag: Jede Klasse, die ProductDao implementiert, stellt dieselben vier Methoden bereit.

public interface ProductDao {
    List<Product> findAll();
    Product findById(int id);
    void save(Product p);
    void deleteById(int id);
}

ProductService verlässt sich auf diesen Vertrag. Welche Klasse ihn erfüllt, ist ihm egal. Das ist DIP.

ImportantAusblick: Kapitel 4

Das DAO-Pattern baut direkt auf DIP auf. Kapitel 4 (?sec-dao-pattern) zeigt, wie ProductDao, InMemoryProductDao, TextFileProductDao und MariaDbProductDao zusammenspielen — und wie dieser Aufbau im Code konkret aussieht. DIP ist der Grund, warum das DAO-Pattern so funktioniert, wie es funktioniert.

4.7 SOLID im Zusammenspiel

Die fünf SOLID-Prinzipien sind keine isolierten Regeln. Sie greifen ineinander.

SRP sorgt dafür, dass ProductService keine Datenzugriffslogik enthält. OCP macht es möglich, neue DAO-Varianten hinzuzufügen, ohne bestehenden Code zu ändern. DIP erklärt, warum ProductService vom Interface ProductDao abhängt — und nicht von einer konkreten Klasse.

Alle drei treffen sich im ProductDao-Interface. Das Interface ist kein Zufallsprodukt. Es ist die direkte Konsequenz dieser drei Prinzipien.

LSP stellt sicher, dass alle DAO-Implementierungen wirklich austauschbar sind — dass InMemoryProductDao sich genauso verhält wie erwartet, und MariaDbProductDao ebenso. ISP hält das Interface schlank — nur die vier Methoden, die wirklich gebraucht werden.

Ein Programm, das diese fünf Prinzipien einhält, lässt sich leichter testen, leichter erweitern und leichter warten. Das ist das Ziel von SOLID.

4.8 Zusammenfassung

Prinzip Kurzaussage Im Beispiel
S Single Responsibility Eine Klasse, eine Aufgabe ProductView zeigt nur an; ProductService enthält nur Logik; ProductDao greift nur auf Daten zu
O Open/Closed Erweiterung durch neue Klassen Neue DAO-Variante → neue Klasse; ProductService bleibt unverändert
L Liskov Substitution Untertypen sind austauschbar InMemoryProductDao, TextFileProductDao, MariaDbProductDao sind jederzeit durch ProductDao ersetzbar
I Interface Segregation Kleine, spezifische Interfaces ProductDao hat genau vier Methoden
D Dependency Inversion Vom Interface abhängen, nicht von der Klasse ProductService kennt ProductDao, nicht MariaDbProductDao
TipMerksatz

SRP, OCP und DIP treffen sich im ProductDao-Interface. Das Interface ist keine optionale Ergänzung — es ist die Konsequenz dieser Prinzipien.
