Appendix B — Glossar

NoteHinweis

Dieses Glossar erklärt alle Fachbegriffe, die im Begleitheft verwendet werden. Die Einträge sind alphabetisch sortiert. Beim Lesen eines Kapitels kann hier jederzeit nachgeschlagen werden.

@Override. Eine Java-Annotation, die kennzeichnet, dass eine Methode aus einem Interface oder einer Elternklasse implementiert wird. Ist der Methodenname falsch geschrieben, meldet der Compiler sofort einen Fehler.

Abhängigkeit (dependency). Eine Klasse hängt von einer anderen ab, wenn sie deren Typ kennt und verwendet. Abhängigkeiten von konkreten Klassen machen Code schwer änderbar; Abhängigkeiten von Interfaces sind flexibler.

ArrayList. Eine Implementierung des List-Interface in Java. Sie speichert Objekte in dynamisch wachsender Reihenfolge im Arbeitsspeicher und ist die am häufigsten verwendete Listenvariante.

Attribut. Eine Variable, die den Zustand eines Objekts beschreibt und innerhalb einer Klasse deklariert ist. Attribute sind typischerweise private und werden über Getter und Setter zugänglich gemacht.

Backend. Die unterste Schicht in einer N-Tier-Architektur; zuständig für den Datenzugriff. Im Begleitheft übernimmt ProductDao (bzw. seine Implementierungen) diese Rolle.

BufferedReader / BufferedWriter. Java-Klassen aus dem Paket java.io zum zeilenweisen Lesen und Schreiben von Textdateien. Sie puffern Daten im Arbeitsspeicher, um viele einzelne Dateizugriffe zu vermeiden.

Business Logic (Geschäftslogik). Die mittlere Schicht in einer N-Tier-Architektur; enthält die Regeln und Verarbeitungslogik des Programms. Im Begleitheft entspricht das der Klasse ProductService.

Connection. Eine JDBC-Klasse, die eine offene Verbindung zu einer Datenbank repräsentiert. Sie wird mit DriverManager.getConnection(url, user, password) geöffnet und nach Verwendung geschlossen.

CRUD. Akronym für die vier grundlegenden Datenzugriffsoperationen: Create (Erstellen), Read (Lesen), Update (Aktualisieren), Delete (Löschen). Das ProductDao-Interface deckt diese vier Operationen ab.

CSV (Comma-Separated Values). Ein einfaches Textformat, bei dem Felder durch ein Trennzeichen getrennt sind. TextFileProductDao speichert Produkte im Format id;name;price, wobei Semikolon als Trennzeichen dient.

DAO (Data Access Object — Datenzugriffsobjekt). Ein Entwurfsmuster, das den gesamten Datenzugriff in einer eigenen Klasse kapselt. Der Rest des Programms kommuniziert nur mit dem Interface, nicht mit der konkreten Implementierung.

Dependency Injection (Abhängigkeitsinjektion). Ein Entwurfsmuster, bei dem Abhängigkeiten einer Klasse von außen übergeben werden — zum Beispiel im Konstruktor — statt intern erzeugt zu werden. ProductService erhält sein dao-Objekt per Dependency Injection.

DIP (Dependency Inversion Principle — Abhängigkeitsumkehrprinzip). Das fünfte SOLID-Prinzip: Klassen sollen von Abstraktionen (Interfaces) abhängen, nicht von konkreten Implementierungen. Es erklärt, warum ProductService vom Interface ProductDao abhängt — und nicht von MariaDbProductDao.

Frontend (Präsentationsschicht). Die oberste Schicht in einer N-Tier-Architektur; zuständig für Anzeige und Eingabe. Im Begleitheft übernimmt ProductView diese Rolle.

Getter / Setter. Methoden, die den kontrollierten Lese- und Schreibzugriff auf private Attribute ermöglichen. Ein Getter gibt den Wert zurück (getName()), ein Setter setzt ihn (setName(String name)).

Implementierung. Eine konkrete Klasse, die ein Interface umsetzt. InMemoryProductDao, TextFileProductDao und MariaDbProductDao sind Implementierungen des Interface ProductDao.

InMemoryProductDao. Die einfachste DAO-Implementierung im Begleitheft. Sie speichert Produkte in einer ArrayList im Arbeitsspeicher — ohne Datei und ohne Datenbank. Daten gehen beim Programmende verloren.

In-Memory. Wörtlich „im Speicher” — bezeichnet Datenspeicherung, die ausschließlich im Arbeitsspeicher (RAM) stattfindet. Diese Variante eignet sich ideal für Tests und erste Implementierungen, bietet aber keine Persistenz.

Interface (Schnittstelle). Eine Java-Konstruktion, die Methoden vorschreibt, ohne sie auszuprogrammieren. Es ist ein Vertrag: Jede implementierende Klasse muss alle Methoden bereitstellen.

ISP (Interface Segregation Principle — Schnittstellentrennungsprinzip). Das vierte SOLID-Prinzip: Viele kleine, spezifische Interfaces sind besser als ein großes, allgemeines. ProductDao enthält genau die vier Methoden, die alle Implementierungen tatsächlich brauchen — nicht mehr.

JDBC (Java Database Connectivity). Die Standard-API in Java für den Zugriff auf relationale Datenbanken. JDBC ist Teil von Java und stellt Klassen wie Connection, PreparedStatement und ResultSet bereit.

Kapselung (Encapsulation). Ein Grundprinzip der objektorientierten Programmierung: Attribute sind private, der Zugriff erfolgt nur über definierte Methoden. So bleibt das Objekt immer in einem gültigen Zustand.

Klasse. Ein Bauplan für Objekte in Java. Sie legt fest, welche Attribute (Daten) und Methoden (Verhalten) ein Objekt hat.

Konstruktor. Eine spezielle Methode, die beim Erstellen eines Objekts mit new automatisch aufgerufen wird. Seine Aufgabe ist es, die Startwerte der Attribute zu setzen.

Kopplung (coupling). Das Ausmaß, in dem Klassen voneinander abhängen. Starke Kopplung macht Änderungen riskant; schwache Kopplung — etwa durch Interfaces — macht Code wartbar und testbar.

Lambda-Ausdruck. Eine kurze Schreibweise für eine anonyme Funktion in Java (ab Java 8). Beispiel: p -> p.getId() == id in removeIf() — übersetzt als: „für jedes p gilt: seine ID ist gleich id.”

List. Ein Interface in Java für geordnete Listen. ArrayList ist die häufigste Implementierung. List<Product> ist eine typsichere Liste, die ausschließlich Product-Objekte enthält.

LSP (Liskov Substitution Principle — Liskovsches Substitutionsprinzip). Das dritte SOLID-Prinzip: Überall, wo ein Objekt eines Typs erwartet wird, muss ein Objekt eines Untertyps korrekt funktionieren. Alle DAO-Implementierungen müssen sich so verhalten, wie es das ProductDao- Interface verspricht — nicht nur syntaktisch, sondern inhaltlich.

MariaDB. Ein relationales, quelloffenes Datenbanksystem, das SQL versteht und mit MySQL kompatibel ist. Im Begleitheft wird MariaDB als Datenquelle für MariaDbProductDao verwendet.

MariaDB Connector/J. Eine JAR-Bibliothek, die JDBC für MariaDB umsetzt. Sie ermöglicht Java-Programmen die Kommunikation mit einer MariaDB-Datenbank. Ohne diese Datei im Projekt ist kein Datenbankzugriff möglich.

MariaDbProductDao. Die professionellste DAO-Implementierung im Begleitheft. Sie kommuniziert über JDBC mit einer MariaDB-Datenbank und ist persistent sowie transaktionssicher.

Methode. Ein benannter Codeblock innerhalb einer Klasse, der eine Aktion ausführt oder einen Wert zurückgibt. Methoden beschreiben das Verhalten eines Objekts.

N-Tier-Architektur (N-Schichten-Architektur). Ein Architekturmuster, das ein Programm in übereinanderliegende Schichten (Tiers oder Layers) aufteilt. Jede Schicht hat genau eine Aufgabe und kommuniziert nur mit der direkt benachbarten Schicht. Bei drei Schichten spricht man von 3-Tier.

Objekt. Eine konkrete Instanz einer Klasse, erzeugt mit new. Jedes Objekt hat seine eigenen Attributwerte und kann die Methoden der Klasse verwenden.

OCP (Open/Closed Principle — Offen-geschlossen-Prinzip). Das zweite SOLID-Prinzip: Eine Klasse soll offen für Erweiterung sein, aber geschlossen für Änderung. Neue Datenquellen werden als neue Klassen eingeführt — ohne bestehenden Code zu ändern.

Package. Eine Gruppierung von Java-Klassen, die inhaltlich zusammengehören. Der Package-Name entspricht dem Ordnernamen im Dateisystem und organisiert größere Projekte übersichtlich.

Persistenz. Die Eigenschaft, dass Daten auch nach dem Programmende erhalten bleiben. TextFileProductDao und MariaDbProductDao sind persistente Varianten; InMemoryProductDao ist es nicht.

POJO (Plain Old Java Object). Ein einfaches Java-Objekt ohne besondere Abhängigkeiten. Die Klasse Product ist ein POJO: Sie enthält nur Daten und Getter, aber keine Datenbankverbindungen, keine Dateioperationen und keine Anzeigelogik.

Polymorphismus. Die Eigenschaft, dass eine Variable vom Typ eines Interface jede beliebige Implementierung halten kann. Beispiel: ProductDao dao = new InMemoryProductDao() — die Variable dao hat den Typ des Interface, das Objekt dahinter ist eine konkrete Implementierung.

PreparedStatement. Eine JDBC-Klasse zum sicheren Ausführen von SQL-Abfragen mit Platzhaltern (?). Sie verhindert SQL-Injection, indem Eingabewerte getrennt vom SQL-Text übergeben werden.

Product. Die Domänenklasse im Begleitheft; repräsentiert ein Produkt mit den Feldern id, name und price. Sie ist ein POJO und enthält keine Datenzugriffs- oder Anzeigelogik.

ProductDao. Das Interface, das die vier Datenzugriffsmethoden vorschreibt: findAll(), findById(int id), save(Product p), deleteById(int id). Es ist der Vertrag, den alle DAO-Implementierungen erfüllen müssen.

ProductService. Die Klasse der Business-Logic-Schicht. Sie prüft Eingaben, koordiniert Abläufe und delegiert den Datenzugriff an ProductDao — ohne zu wissen, welche Implementierung dahintersteckt.

ProductView. Die Klasse der Präsentationsschicht. Sie zeigt Produkte an und nimmt Eingaben entgegen; enthält keine Datenzugriffs- oder Verarbeitungslogik.

Refactoring. Das Umstrukturieren von Code, ohne sein äußeres Verhalten zu ändern. Ziel ist eine klarere Trennung der Verantwortlichkeiten und damit bessere Wartbarkeit.

Relationale Datenbank. Ein Datenbanksystem, das Daten in Tabellen speichert. Tabellen bestehen aus Zeilen (einzelnen Datensätzen) und Spalten (Datenfeldern) und können über gemeinsame Felder verknüpft werden.

ResultSet. Eine JDBC-Klasse, die das Ergebnis einer SELECT-Abfrage enthält. Das ResultSet wird zeilenweise mit rs.next() durchlaufen; Spaltenwerte werden mit rs.getInt(), rs.getString() usw. ausgelesen.

Schicht (tier, layer). Eine Gruppe von Klassen mit einer gemeinsamen Aufgabe in einer N-Tier-Architektur. Im Begleitheft gibt es drei Schichten: Frontend, Business Logic und Backend.

Separation of Concerns (Trennung der Zuständigkeiten). Das Prinzip, jede Klasse für genau eine klar abgegrenzte Aufgabe verantwortlich zu machen. Es ist die konzeptionelle Grundlage von N-Tier-Architektur und SRP.

Setter → Getter / Setter

SOLID. Ein Akronym für fünf Prinzipien des objektorientierten Softwareentwurfs: Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion. Formuliert und popularisiert von Robert C. Martin Anfang der 2000er-Jahre.

SQL (Structured Query Language). Die Sprache zum Abfragen und Verändern relationaler Datenbanken. Grundbefehle: SELECT (lesen), INSERT (einfügen), UPDATE (ändern), DELETE (löschen).

SQL-Injection. Ein Angriff, bei dem schädliche SQL-Befehle über Eingabefelder eingeschleust werden. PreparedStatement mit Platzhaltern verhindert SQL-Injection, weil Eingabewerte nicht direkt in den SQL-Text eingebaut werden.

SRP (Single Responsibility Principle — Prinzip der einzigen Verantwortung). Das erste SOLID-Prinzip: Eine Klasse hat genau eine Aufgabe — und damit genau einen Grund, sich zu ändern. ProductView zeigt an, ProductService verarbeitet, ProductDao speichert.

TextFileProductDao. Eine DAO-Implementierung, die Produkte als CSV-Textdatei auf dem Dateisystem speichert. Sie ist persistent — Daten bleiben nach dem Programmende erhalten —, aber nicht transaktionssicher.

Transaktionssicherheit (Transaktionsintegrität). Die Eigenschaft eines Datenbanksystems, sicherzustellen, dass Schreibvorgänge vollständig oder gar nicht ausgeführt werden. MariaDB ist transaktionssicher; TextFileProductDao ist es nicht.

Untertyp. Eine Klasse, die ein Interface implementiert oder eine andere Klasse erweitert. Im Kontext des LSP: Ein Untertyp muss überall verwendbar sein, wo der übergeordnete Typ erwartet wird — ohne das Programm zum Absturz zu bringen.

Vertrag. Die metaphorische Bezeichnung für ein Interface: Es legt fest, welche Methoden bereitgestellt werden müssen. Jede Klasse, die das Interface mit implements übernimmt, verpflichtet sich, alle Methoden korrekt zu implementieren.
