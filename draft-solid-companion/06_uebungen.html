7  Übungen

NoteLernziele

Nach diesem Kapitel kannst du …

  • Klassen und Methoden den richtigen Schichten einer N-Tier-Architektur zuordnen.
  • Verstöße gegen SOLID-Prinzipien in Java-Code erkennen und benennen.
  • erklären, wozu ein DAO-Interface dient und welche Methoden es enthält.
  • einfachen Java-Code lesen, analysieren und Fehler begründen.
  • bestehenden Code durch gezieltes Refactoring verbessern.
  • für eine gegebene Anforderung die passende DAO-Variante wählen und begründen.

Die Aufgaben sind in sechs Gruppen gegliedert: N-Tier, SOLID, DAO-Pattern, Code lesen, Refactoring und Transfer. Innerhalb jeder Gruppe steigen die Aufgaben im Schwierigkeitsgrad:

  • ⬜ leicht — Zuordnen, Erkennen
  • 🟨 mittel — Analysieren, Anwenden
  • 🟥 herausfordernd — Erklären, Begründen, Entwerfen

Die Musterlösungen stehen am Ende dieses Kapitels (Section 7.8).

7.1 Begriffe zur Wiederholung

Bevor du mit den Aufgaben beginnst: Kannst du diese Begriffe erklären?

Begriff Bedeutung
N-Tier Programm in Schichten aufgeteilt
Frontend Präsentationsschicht — gibt Daten aus, nimmt Eingaben entgegen
Business Logic Logikschicht — verarbeitet und prüft Daten
Backend Datenzugriffsschicht — liest und schreibt Daten
DAO Data Access Object — kapselt den Datenzugriff
Interface Vertrag: legt Methoden fest, ohne sie zu implementieren
SRP, OCP, DIP Drei SOLID-Prinzipien mit direktem Bezug zum DAO-Pattern

Decke die rechte Spalte ab und erkläre jeden Begriff in eigenen Worten. Dann prüfe dich selbst.

7.2 Aufgaben: N-Tier

Die drei Schichten tragen klare Verantwortlichkeiten. Das Frontend zeigt Daten an und nimmt Eingaben entgegen. Die Business Logic prüft und verarbeitet Daten. Das Backend liest und schreibt Daten.

Jede Aufgabe in den folgenden N-Tier-Übungen dreht sich um diese Zuordnung.

7.2.1 Aufgabe N1 ⬜

Ordne zu: Welche Aussage gehört zu welcher Schicht?

Aussage Schicht
„Zeigt eine Liste von Produkten auf dem Bildschirm an.” ?
„Prüft, ob der Preis eines Produkts größer als 0 ist.” ?
„Liest alle Produkte aus einer Textdatei.” ?
„Nimmt eine Eingabe vom Benutzer entgegen.” ?
„Speichert ein neues Produkt in der Datenbank.” ?

Mögliche Antworten: Frontend · Business Logic · Backend

Welche Klasse gehört zu welcher Schicht?

Ordne jede Klasse der richtigen Schicht zu:

ProductView
ProductService

7.2.4 Aufgabe N4 🟥

Entwirf die Struktur:

Ein Programm soll Produkte verwalten. Beschreibe die Architektur — ohne Code zu schreiben:

  1. Welche Klassen gibt es?
  2. Welche Schicht gehört zu welcher Klasse?
  3. Welche Klasse kennt welche andere Klasse? Beispiel: „ProductView kennt ProductService.”
  4. Welche Klasse kennt welche nicht? Beispiel: „ProductView kennt ProductDao nicht.”

7.3 Aufgaben: SOLID

Die folgenden Aufgaben beziehen sich auf alle fünf Prinzipien. Am häufigsten kommen SRP, OCP und DIP vor — sie stehen in direktem Zusammenhang mit dem DAO-Pattern (siehe ?sec-dao-pattern).

7.3.1 Aufgabe S1 ⬜

Single Responsibility Principle — Erkenne den Verstoß:

public class Product {
    private String name;
    private double price;

    public String getName()  { return name; }
    public double getPrice() { return price; }

    public void saveToFile() {
        // Produkt in Datei schreiben
    }

    public void printLabel() {
        // Produkt auf Drucker ausgeben
    }
}

Beantworte folgende Fragen:

  1. Wie viele verschiedene Aufgaben hat diese Klasse?
  2. Welche Methoden sollten nicht in Product stehen?
  3. In welche Klassen würden diese Methoden besser passen?

7.3.2 Aufgabe S2 ⬜

Open/Closed Principle — Was ist besser?

Variante A:

public List<Product> getAll(String type) {
    if (type.equals("memory")) { /* ... */ }
    else if (type.equals("file"))   { /* ... */ }
    else if (type.equals("db"))     { /* ... */ }
    return null;
}

Variante B:

public List<Product> getAll() {
    return dao.findAll();
}

Welche Variante folgt dem Open/Closed Principle? Begründe deine Antwort.

Hinweis: Das OCP besagt, dass Code offen für Erweiterung, aber geschlossen für Änderung sein soll.

7.3.3 Aufgabe S3 🟨

Dependency Inversion Principle — Erkenne das Problem:

public class ProductService {
    private MariaDbProductDao dao = new MariaDbProductDao();

    public List<Product> getAll() {
        return dao.findAll();
    }
}

Beantworte folgende Fragen:

  1. Wovon hängt ProductService hier ab — von einem Interface oder von einer konkreten Klasse?
  2. Was passiert, wenn statt MariaDB eine Textdatei verwendet werden soll?
  3. Wie sollte der Code geändert werden, damit ProductService vom Interface abhängt?

7.3.4 Aufgabe S4 🟨

SOLID — Welches Prinzip wird verletzt?

Ordne jeder Situation das passende SOLID-Prinzip zu:

# Situation Prinzip
1 ProductView speichert Daten selbst in eine Datei. ?
2 ProductService enthält direkt new MariaDbProductDao(). ?
3 Neue Datenquelle erfordert Änderung in ProductService. ?
4 Das Interface hat 20 Methoden, jede Klasse braucht aber nur 3 davon. ?

Mögliche Antworten: SRP · OCP · DIP · ISP

7.3.5 Aufgabe S5 🟥

Erkläre in eigenen Worten:

„ProductService hängt von ProductDao ab — nicht von MariaDbProductDao.”

Beantworte folgende Fragen:

  1. Was bedeutet „abhängen” in diesem Satz?
  2. Warum ist das ein Vorteil?
  3. Nenne ein konkretes Beispiel, bei dem dieser Vorteil sichtbar wird.

7.4 Aufgaben: DAO-Pattern

Das DAO-Pattern trennt den Datenzugriff vom Rest des Programms. Das Interface ProductDao legt den Vertrag fest. Die Implementierungen erfüllen diesen Vertrag auf unterschiedliche Arten.

7.4.1 Aufgabe D1 ⬜

Erkläre in einem Satz:

Was ist die Aufgabe eines DAO?

Tipp: Denke an die Abkürzung — Data Access Object.

7.4.2 Aufgabe D2 ⬜

Interface oder Implementierung?

Ordne jede Klasse zu:

ProductDao
InMemoryProductDao
TextFileProductDao
MariaDbProductDao
Interface Implementierungen
? ?

7.4.3 Aufgabe D3 🟨

Was fehlt?

public interface ProductDao {
    List<Product> findAll();
    Product findById(int id);
    // hier fehlt etwas ...
}

Das Interface zeigt nur zwei Methoden. Welche zwei Methoden fehlen laut Konvention noch? Schreibe die Methodensignaturen auf.

Hinweis: Ein vollständiges DAO deckt die vier CRUD-Operationen ab — Create, Read, Update, Delete.

7.4.4 Aufgabe D4 🟨

Wogegen ist ProductService programmiert?

public class ProductService {
    private ProductDao dao;

    public ProductService(ProductDao dao) {
        this.dao = dao;
    }

    public List<Product> getAll() {
        return dao.findAll();
    }
}

Beantworte folgende Fragen:

  1. Von welchem Typ ist die Variable dao?
  2. Kann dao auch ein InMemoryProductDao sein? Warum?
  3. Wie nennt man dieses Entwurfsmuster?

7.4.5 Aufgabe D5 🟥

Vervollständige die Klasse:

public class InMemoryProductDao implements ProductDao {

    private List<Product> products = new ArrayList<>();

    @Override
    public List<Product> findAll() {
        // hier eintragen
    }

    @Override
    public Product findById(int id) {
        // hier eintragen
    }

    @Override
    public void save(Product product) {
        // hier eintragen
    }

    @Override
    public void deleteById(int id) {
        // hier eintragen
    }
}

Implementiere alle vier Methoden. products ist eine ArrayList — du kannst add(), removeIf() und eine for-each-Schleife verwenden.

7.5 Aufgaben: Code lesen

Beim Lesen von Code ist es hilfreich, die Aufrufkette zu verfolgen. Wer ruft wen auf? Was kommt zurück? Welche Schicht liegt wo?

7.5.1 Aufgabe C1 ⬜

Lies den Code und beantworte die Fragen:

ProductDao dao = new TextFileProductDao();
ProductService service = new ProductService(dao);
ProductView view = new ProductView(service);

view.showAllProducts();
  1. Welche DAO-Variante wird hier verwendet?
  2. Wer kennt wen? Zeichne oder beschreibe die Abhängigkeiten.
  3. Was passiert, wenn view.showAllProducts() aufgerufen wird? Beschreibe den Ablauf in Schritten.

7.5.2 Aufgabe C2 🟨

Was macht dieser Code — und was ist daran problematisch?

public class ProductService {
    private ProductDao dao;

    public Product getCheapest() {
        List<Product> all = dao.findAll();
        Product cheapest = all.get(0);
        for (Product p : all) {
            if (p.getPrice() < cheapest.getPrice()) {
                cheapest = p;
            }
        }
        return cheapest;
    }
}
  1. Was macht die Methode getCheapest()?
  2. Was könnte bei all.get(0) schiefgehen?
  3. Welcher Schicht gehört diese Logik — und ist das korrekt?

7.5.3 Aufgabe C3 🟥

Lies den Code und erkläre, was hier falsch ist:

public class ProductView {
    private InMemoryProductDao dao = new InMemoryProductDao();

    public void showAll() {
        List<Product> products = dao.findAll();
        for (Product p : products) {
            System.out.println(p.getName());
        }
    }

    public void add(String name, double price) {
        Product p = new Product(1, name, price);
        dao.save(p);
    }
}

Benenne mindestens drei Probleme mit Bezug auf N-Tier und SOLID. Begründe jedes Problem kurz.

7.6 Aufgaben: Refactoring

Refactoring bedeutet: Code umstrukturieren, ohne das Verhalten zu ändern. Das Ziel ist immer eine klarere Trennung der Verantwortlichkeiten.

7.6.1 Aufgabe R1 🟨

Refactoring: Direkte Abhängigkeit auflösen

Dieser Code hat ein DIP-Problem:

public class ProductService {
    private MariaDbProductDao dao = new MariaDbProductDao();

    public List<Product> getAll() {
        return dao.findAll();
    }
}

Schreibe den Code so um, dass ProductService vom Interface ProductDao abhängt — nicht von MariaDbProductDao.

Hinweis: Verwende einen Konstruktor, der ProductDao als Parameter nimmt.

7.6.2 Aufgabe R2 🟨

Refactoring: Schichten trennen

Dieser Code verstößt gegen SRP und die N-Tier-Trennung:

public class ProductView {
    public void run() {
        List<Product> products = new ArrayList<>();
        products.add(new Product(1, "Laptop", 999.99));
        products.add(new Product(2, "Maus",    19.99));

        for (Product p : products) {
            System.out.println(p.getName() + ": " + p.getPrice());
        }
    }
}

Verteile den Code auf die richtigen Klassen: ProductView, ProductService, InMemoryProductDao.

Du musst keinen vollständigen Code schreiben — eine Skizze mit den wichtigsten Methoden genügt.

7.6.3 Aufgabe R3 🟥

Refactoring: Neue Variante ohne Code-Änderung

Gegeben ist dieser funktionierende Code:

ProductDao dao = new InMemoryProductDao();
ProductService service = new ProductService(dao);
ProductView view = new ProductView(service);
  1. Ändere den Code so, dass statt des Speichers eine Textdatei verwendet wird. Nur eine Zeile darf geändert werden.
  2. Was bleibt unverändert?
  3. Welches SOLID-Prinzip macht das möglich? Begründe deine Antwort.

7.7 Aufgaben: Transfer

Die Transfer-Aufgaben verlangen keine Formeln, sondern Argumente. Es geht darum, eine Entscheidung zu begründen — nicht darum, eine einzige richtige Antwort zu finden.

7.7.1 Aufgabe T1 ⬜

Wann welche Variante?

Entscheide für jede Situation, welche DAO-Variante am sinnvollsten ist:

Situation Variante
Du willst die Methoden zuerst testen — ohne Datenbank-Setup. ?
Die Daten sollen nach dem Programmende erhalten bleiben — ohne Datenbank. ?
Das Programm soll in einem professionellen Betrieb eingesetzt werden. ?
Du fängst neu an und willst schnell ein erstes Ergebnis sehen. ?

Mögliche Antworten: InMemoryProductDao · TextFileProductDao · MariaDbProductDao

7.7.2 Aufgabe T2 🟨

Begründe deine Wahl:

Ein Entwickler schreibt ein kleines Verwaltungsprogramm. Die Daten sollen erhalten bleiben, wenn das Programm geschlossen wird. Eine Datenbank ist nicht verfügbar.

  1. Welche DAO-Variante empfiehlst du?
  2. Welchen Vorteil hat diese Variante gegenüber den anderen?
  3. Welchen Nachteil hat sie?

7.7.3 Aufgabe T3 🟥

Diskutiere:

„Wenn wir von Anfang an eine Datenbank verwenden würden, bräuchten wir das Interface ProductDao gar nicht.”

Stimmt diese Aussage? Begründe deine Antwort mit Bezug auf mindestens zwei SOLID-Prinzipien.

7.8 Musterlösungen

Die folgenden Lösungen sind Richtwerte — keine starren Vorgaben. Bei Begründungsaufgaben zählt die Argumentation, nicht die exakte Formulierung.

7.8.1 Lösung N1

Aufgabe N1 — Zuordnung der Aussagen (Section 7.2.1)

Aussage Schicht
„Zeigt eine Liste von Produkten auf dem Bildschirm an.” Frontend
„Prüft, ob der Preis eines Produkts größer als 0 ist.” Business Logic
„Liest alle Produkte aus einer Textdatei.” Backend
„Nimmt eine Eingabe vom Benutzer entgegen.” Frontend
„Speichert ein neues Produkt in der Datenbank.” Backend

7.8.2 Lösung N2

Aufgabe N2 — Klassen und Schichten (Section 7.2.2)

Schicht Klassen
Frontend ProductView
Business Logic ProductService
Backend InMemoryProductDao, TextFileProductDao, MariaDbProductDao

7.8.3 Lösung N3

Aufgabe N3 — Fehler in ProductView (Section 7.2.3)

ProductView ist das Frontend — ihre Aufgabe ist ausschließlich die Anzeige.

Den Datenbankzugriff direkt in der View zu haben verletzt das Single Responsibility Principle: ProductView hat jetzt zwei Gründe zur Änderung — eine Änderung der Darstellung und eine Änderung der Datenbankverbindung.

Außerdem verstößt der Code gegen die N-Tier-Trennung: Das Frontend spricht direkt mit dem Backend, ohne die Business Logic zu durchlaufen.

Korrekte Aufrufkette:

ProductView → ProductService → ProductDao

7.8.4 Lösung N4

Aufgabe N4 — Struktur eines Produktverwaltungsprogramms (Section 7.2.4)

Klassen:
  ProductView       → Frontend
  ProductService    → Business Logic
  ProductDao        → Interface (Backend-Vertrag)
  InMemoryProductDao, TextFileProductDao, MariaDbProductDao → Backend

Abhängigkeiten (wer kennt wen):
  ProductView      kennt ProductService
  ProductService   kennt ProductDao (das Interface)
  DAO-Implementierungen kennen Product

Keine Abhängigkeiten:
  ProductView      kennt ProductDao nicht
  ProductService   kennt InMemoryProductDao etc. nicht direkt

7.8.5 Lösung S1

Aufgabe S1 — SRP-Verstoß in Product (Section 7.3.1)

Product hat drei verschiedene Aufgaben: Daten halten, Datei schreiben, Drucken. Das verstößt gegen das Single Responsibility Principle.

saveToFile() und printLabel() sollten nicht in Product stehen.

Korrekte Aufteilung:

Methode Gehört in
saveToFile() TextFileProductDao
printLabel() ProductView oder eigene Druckerklasse
Getter Product (bleibt)

Product selbst soll nur Daten halten — ein sogenanntes POJO (Plain Old Java Object).

7.8.6 Lösung S2

Aufgabe S2 — Open/Closed Principle (Section 7.3.2)

Variante B folgt dem OCP.

In Variante A muss getAll() bei jeder neuen Datenquelle geändert werden. Jede neue if-Verzweigung erweitert denselben Code.

In Variante B bleibt getAll() unverändert. Eine neue Datenquelle wird durch eine neue Klasse eingeführt, die ProductDao implementiert — der bestehende Code wird nicht angetastet.

Offen für Erweiterung, geschlossen für Änderung.

7.8.7 Lösung S3

Aufgabe S3 — DIP-Problem (Section 7.3.3)

ProductService hängt direkt von MariaDbProductDao ab — einer konkreten Klasse.

Wenn eine Textdatei verwendet werden soll, muss ProductService geändert werden — obwohl er inhaltlich nichts mit der Datenspeicherung zu tun hat.

Korrekte Version mit Konstruktor:

public class ProductService {
    private ProductDao dao;

    public ProductService(ProductDao dao) {
        this.dao = dao;
    }

    public List<Product> getAll() {
        return dao.findAll();
    }
}

Verwendung außerhalb:

ProductDao dao = new MariaDbProductDao();
ProductService service = new ProductService(dao);

Jetzt hängt ProductService vom Interface ab — nicht von der Implementierung. Die konkrete Klasse wird von außen übergeben. Das nennt man Dependency Injection.

7.8.8 Lösung S4

Aufgabe S4 — Welches SOLID-Prinzip wird verletzt? (Section 7.3.4)

# Situation Prinzip
1 ProductView speichert Daten selbst in eine Datei. SRP
2 ProductService enthält direkt new MariaDbProductDao(). DIP
3 Neue Datenquelle erfordert Änderung in ProductService. OCP
4 Interface hat 20 Methoden, jede Klasse braucht nur 3. ISP

7.8.9 Lösung S5

Aufgabe S5 — DIP in eigenen Worten (Section 7.3.5)

1. Abhängen bedeutet: ProductService kennt den Typ ProductDao (das Interface). Er ruft dao.findAll() auf — ohne zu wissen, welche konkrete Klasse dahinter steckt.

2. Vorteil: Die Implementierung kann ausgetauscht werden, ohne ProductService zu ändern.

3. Beispiel: Beim Testen wird InMemoryProductDao verwendet — kein Datenbank-Setup nötig. Im Betrieb wird MariaDbProductDao eingesetzt. ProductService bleibt in beiden Fällen identisch.

7.8.10 Lösung D1

Aufgabe D1 — Aufgabe eines DAO (Section 7.4.1)

Ein DAO kapselt den gesamten Datenzugriff, damit der Rest des Programms nicht wissen muss, wie und wo Daten gespeichert sind.

Kurz gesagt: Ein DAO ist die einzige Klasse, die „weiß”, woher die Daten kommen.

7.8.11 Lösung D2

Aufgabe D2 — Interface oder Implementierung? (Section 7.4.2)

Interface Implementierungen
ProductDao InMemoryProductDao, TextFileProductDao, MariaDbProductDao

7.8.12 Lösung D3

Aufgabe D3 — Fehlende Methoden im Interface (Section 7.4.3)

Die beiden fehlenden Methoden:

void save(Product product);
void deleteById(int id);

Alle vier Standardmethoden des ProductDao-Interface:

List<Product> findAll();
Product findById(int id);
void save(Product product);
void deleteById(int id);

Diese vier Methoden entsprechen den vier CRUD-Operationen: Create (save), Read (findAll, findById), Delete (deleteById).

7.8.13 Lösung D4

Aufgabe D4 — Wogegen ist ProductService programmiert? (Section 7.4.4)

1. dao ist vom Typ ProductDao — das Interface.

2. Ja. InMemoryProductDao implementiert ProductDao. Überall, wo ProductDao erwartet wird, kann jede beliebige Implementierung eingesetzt werden.

3. Fachbegriffe: Dependency Inversion Principle (DIP) und Dependency Injection.

7.8.14 Lösung D5

Aufgabe D5 — InMemoryProductDao vervollständigen (Section 7.4.5)

@Override
public List<Product> findAll() {
    return products;
}

@Override
public Product findById(int id) {
    for (Product p : products) {
        if (p.getId() == id) return p;
    }
    return null;
}

@Override
public void save(Product product) {
    products.add(product);
}

@Override
public void deleteById(int id) {
    products.removeIf(p -> p.getId() == id);
}

removeIf mit Lambda-Ausdruck ist die kompakte Variante. Wer Lambdas noch nicht kennt, kann stattdessen eine normale for-Schleife verwenden:

@Override
public void deleteById(int id) {
    for (int i = 0; i < products.size(); i++) {
        if (products.get(i).getId() == id) {
            products.remove(i);
            return;
        }
    }
}

7.8.15 Lösung C1

Aufgabe C1 — Code lesen (Section 7.5.1)

1. TextFileProductDao — die Textdatei-Variante.

2. Abhängigkeiten:

view → service → dao (ProductDao Interface)
                 ↑
       TextFileProductDao implements ProductDao

3. Ablauf von view.showAllProducts():

view.showAllProducts()
  → service.getAll()
    → dao.findAll()   [TextFileProductDao liest die Datei]
    ← List<Product>
  ← List<Product>
  view gibt Produkte aus

7.8.16 Lösung C2

Aufgabe C2 — getCheapest() (Section 7.5.2)

1. getCheapest() sucht das günstigste Produkt in der Liste.

2. Wenn die Liste leer ist, wirft all.get(0) eine IndexOutOfBoundsException. Korrekte Absicherung:

if (all.isEmpty()) return null;

3. Die Methode gehört in die Business Logic (ProductService) — das ist korrekt. „Welches Produkt ist das günstigste?” ist eine Geschäftsregel. Solche Logik gehört nicht in das Frontend und nicht in das Backend.

7.8.17 Lösung C3

Aufgabe C3 — Mindestens drei Probleme (Section 7.5.3)

# Problem Bezug
1 ProductView hat zwei Aufgaben: anzeigen und Daten hinzufügen. SRP
2 Direkte Abhängigkeit von InMemoryProductDao — kein Interface. DIP
3 View greift direkt auf das Backend zu — die Business Logic fehlt. N-Tier
4 Bei Wechsel der Datenquelle muss ProductView geändert werden. OCP

7.8.18 Lösung R1

Aufgabe R1 — Refactoring: DIP-Problem lösen (Section 7.6.1)

public class ProductService {
    private ProductDao dao;

    public ProductService(ProductDao dao) {
        this.dao = dao;
    }

    public List<Product> getAll() {
        return dao.findAll();
    }
}

Verwendung:

ProductDao dao = new MariaDbProductDao();
ProductService service = new ProductService(dao);

7.8.19 Lösung R2

Aufgabe R2 — Schichten trennen (Skizze) (Section 7.6.2)

// InMemoryProductDao — Backend
private List<Product> products = new ArrayList<>();
public List<Product> findAll() { return products; }
public void save(Product p)    { products.add(p); }

// ProductService — Business Logic
private ProductDao dao;
public List<Product> getAll() { return dao.findAll(); }

// ProductView — Frontend
private ProductService service;
public void showAll() {
    for (Product p : service.getAll()) {
        System.out.println(p.getName() + ": " + p.getPrice());
    }
}

Jede Klasse hat jetzt genau eine Aufgabe.

7.8.20 Lösung R3

Aufgabe R3 — Neue Variante ohne Änderung (Section 7.6.3)

1. Nur diese eine Zeile ändert sich:

ProductDao dao = new TextFileProductDao();

2. Unverändert bleiben: ProductService, ProductView und das Interface ProductDao.

3. Möglich durch OCP und DIP zusammen: ProductService und ProductView hängen vom Interface ab, nicht von der Implementierung. Deshalb kann die Implementierung ausgetauscht werden, ohne irgendetwas sonst zu ändern.

7.8.22 Lösung T2

Aufgabe T2 — Empfehlung: TextFileProductDao (Section 7.7.2)

1. Empfehlung: TextFileProductDao

2. Vorteile: Daten bleiben nach dem Programmende erhalten. Es ist kein externes System nötig. Die Datei ist lesbar und lässt sich einfach prüfen.

3. Nachteile: Keine Transaktionssicherheit — bei einem Absturz können Daten verloren gehen. Langsam bei sehr vielen Datensätzen. Fehleranfällig bei Sonderzeichen im Dateinamen oder im Inhalt.

7.8.23 Lösung T3

Aufgabe T3 — Interface ohne Datenbank? (Section 7.7.3)

Die Aussage ist falsch.

DIP: Ohne Interface hängt ProductService direkt von MariaDbProductDao ab. Jede Änderung der Datenquelle zwingt zur Änderung im Service.

OCP: Ohne Interface lässt sich keine neue Datenquelle hinzufügen, ohne bestehenden Code zu ändern.

Praktischer Zusatzvorteil: Das Interface ermöglicht, während der Entwicklung InMemoryProductDao zu verwenden — ohne echte Datenbank. Das ist unabhängig von SOLID wertvoll.
